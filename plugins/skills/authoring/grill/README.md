# grill

**合意に達するまで1問ずつ問い詰めて、曖昧さを潰す。**

**実装しないし、資料も書かない。** 決めたことと未決を残すところまで。

**分かった気を潰すのが仕事である。**「たぶんこうだろう」で進むと、実装が終わってから前提の違いが出てくる。

## 使う

```
/grill      詰める
```

## 4つの規律

**1問ずつ出す。** まとめて問うと、人は答えやすいものから答える。5問並べると難しい1問が黙って落ち、落ちたことに問うた側も気づかない。

**推奨回答を必ず添える。**「どうしますか？」は、考える仕事をそのまま相手へ渡している。推奨があれば、確認か修正だけで前へ進める。

**調べれば分かることは問わない。** 手元に答えがあるのに聞くのは怠慢である。調べて分かったら「この前提でいく」と宣言してから進む。

**決定は相手に返す。** 事実を埋める仕事をこちらが引き受けるのは、決定だけを相手に残すためである。自分の問いに自分で答えて先へ進んだ実行は、壊れている。

## 決定ログ

**このプラグインだけが状態を持つ。** 素材から作り直せるものは持たない、というのがこの一式の方針だが、**決定は会話の産物で再現できない**。「なぜそう決めたか」は、決めた場に居た人しか書けない。

```bash
scripts/decision.py add --topic <題材> --what <決めたこと> --why <理由> [--status decided|open|dropped]
scripts/decision.py render --topic <題材>     # 決定・未決・取り下げを並べる
```

**理由が空だと書けない。** 理由の無い決定は、後から読んだ人が覆せない（覆していいのかも分からない）。

**未決を無理に決めさせない。**「未決」と書いてあるほうが、間違った決定より役に立つ。会話では決まらない問い（見た目・体感など試して初めて答えられるもの）も未決に置き、何を試せば決まるかを理由に書く。

**取り下げたものも残す。** 消すと、同じ論点が数か月後にまた立つ。

## 合意で閉じる

**問える問いが尽きても、工程はまだ終わっていない。** `render` の出力を提示し、相手が合意したと言うまで閉じない。未決が残ったまま合意することはあるが、合意のないまま次の工程へ進むことはない。

## 設定

```yaml
# <repo>/.harness-plugins/grill.config.yml
version: 1
log_dir: decisions                # 決定ログの置き場
```

設定は自己完結させる。不足値を別の設定層から補わない。

**設定が持つのは決定ログの置き場だけである。** 問い方の規律は grill のアイデンティティであって、環境ごとに変わる値ではないため、`references/questioning.md` に固定してある。

**扱う題材によって着眼点は変わるため、grill自身は題材固有の観点を所有しない。** 単体利用では依頼の文脈を使い、別pluginから呼ぶ場合はそのpluginの指示書に書かれた背景・前提・目的・着眼点を使う。専用のaspect設定はない。

> 0.3.0 で `instructions.questioning.directive` を廃止した。既存の設定にこのキーが残っていると、同梱既定に無い設定として実行が停止する。行ごと削除する。

## うまくいっている兆候

- 問いが1つずつ届き、答えを待ってから次が来る
- どの問いにも推奨と理由が付いている
- 調べれば分かることは「この前提でいく」と宣言して流れていく
- 後の問いが、前の答えを踏まえたものになっている
- 決定ログの理由が埋まっていて、未決が隠されずに残っている
- 合意したと言うまで、実装も資料作成も始まらない

## しないこと

- 実装しない。資料も書かない
- **一度に大量の問いを浴びせない**
- 推奨回答なしで丸投げしない
- **自分の問いに自分で答えない**
- **中身を機械で検査しない。** 問いの数も観点の網羅率も数えない。問いが長く続くのはスコープが大きすぎるサインなので、上限ではなく分割で対処する
