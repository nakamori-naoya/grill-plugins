評価日: 2026-09-15。評価者: この改修を担当したCodexエージェント。
意味評価は同じエージェントによる読解、合成会話の手動トレース、およびこの改修セッションでの実利用者との対話である。独立評価者や別ランタイムによるE2E試験ではない。

## 設計レビュー

責務は「題材と文脈を受け取り、調査と対話によって明示合意した決定結果を一つ保存する」である。
取消ルールを決める対話が該当し、取消機能の実装や合意済み内容から資料を執筆する仕事は該当しない。
内部指示は自分の参照一本だけを読み、兄弟能力、設定、開発repository、既済工程へ依存しない。
公開入口から内部へのリンクは配布package内で完結する。一時directoryへの実配布copyでも構造検査が通る。

旧規律からの継承を次の内容で確認した。

| 評価した主張 | 根拠と判断 |
|---|---|
| 事実を調べ、決定を利用者へ返す | 対話原則1〜6。調査済みの問いを前提へ分類し、自己回答を禁じる。入力の問いが黙って失われない追跡も42に明示 |
| 一問ずつ・推奨と理由 | 原則7〜18。独立した判断を一問に詰め込まず、推奨が問いを否定する場合も問い直す。単に推奨という語を置く規律ではない |
| 前提が揃った上流から問う | 原則19〜24。未決へ依存する論点を後回しにし、他の問いを消す回答を先に得る。件数を終了基準にしない |
| 業務の言葉で問う | 原則25〜28。利用者の語彙を基準にし、題材固有の観点を普遍規則へ拡張しない |
| 未決・取り下げ・理由を保存する | 原則29〜42。判断者不在と試行待ちを区別し、何が分かれば決まるかを残す。理由のない回答は決定へ移さない |
| 明示合意でだけ閉じる | 原則43〜50と内部手順3〜4。空の問い、未決の残存、一覧の修正のすべてで終了合意を求める |
| 独立動作を記述できている | 公開入口は契約入力を内部へ渡し、担当エージェントが同じ会話で実行する。外部から呼ばれても合意を代行しない |

## 移設した8本のBDDの意味評価

BDDは実行コードへ変換せず、以下の判断を読解した。Cucumber等で自動実行した結果ではない。

| シナリオ | 適用した判断 |
|---|---|
| 資料で確定できる事実 | 原則1〜4によって問いから外し、根拠付きの前提を示す |
| 判断者不在 | 原則29〜31によって判断待ちの理由付きopenにする |
| 明示合意なし | 原則45〜46によって合意待ちを維持する |
| 推奨なし | 原則12〜18によってそのまま提示せず、推奨と理由を付けてから提示する |
| 未決の前提あり | 原則19〜22によってL0を先に扱い、L1を後回しにする |
| 複数の論点 | 原則7〜10によって一つを選び、その回答まで次を提示しない |
| 一覧への明示合意 | 原則43〜50によって終了し、内部手順4で結果を保存する |
| 理由なし | 原則36〜39によって理由を確認するまで問いのまま保持する |

## 合成会話の手動トレース

入力と期待行動はscenarios.jsonに固定した。回答はfixture作者が用意した合成回答で、実利用者の合意ではない。

### 単体・典型例

1. 契約入力の題材・目的・読者・範囲・出力先を読み、q1を扱う。
2. 「取消の締切は何を基準にしますか。➡️ 推奨: 出荷日。理由: 在庫引当の解放時点と揃えるため」と一問を構成する。
3. 合成回答「出荷日とし、その理由も採用する」で、q1の回答と理由を保持する。
4. q1の回答・理由と未決なしを一覧にして「この一覧で対話を完了することに合意しますか。➡️ 推奨: この一覧への合意。理由: 回答と採用理由が一覧に反映されているため」と一問を構成する。
5. 合成回答「この決定一覧に合意し、対話を完了してよい」からcompletedのYAMLを作り、fixtures/standalone-output.ymlへ保存してyqで読み戻した。
6. 観測: q1の内容とrationaleが一致し、open_questionsは空配列。合成会話による手順確認であり、ツール付きモデルの自動実行結果ではない。

### 外部・未決と取り下げの境界例

1. fixtures/consumer.ymlのrequiresとplaybook: grillをroot検査へ渡し、構造が受理されることを確認した。
2. その宣言からgrillの公開manifest、公開入口、単一step、内部能力へ至る対応を読解した。
3. 操作感について「➡️ 推奨: 試作後に決める。理由: 実物がないため」と一問を構成する。
4. 合成回答「q1は試作がないため未決。試作を操作して決める」をopenとして保持する。
5. 次に通知について「➡️ 推奨: 対象外とする。理由: 今回は取消操作だけを検証するため」と一問を構成する。
6. 合成回答「q2は今回の対象外なので取り下げる」をwithdrawnとして保持する。
7. 理由付きの未決・取り下げ一覧を示し、未決を残して完了することへの合意を一問で求める。
8. 合成回答「未決と取り下げを含むこの一覧に合意し、対話を完了してよい」からfixtures/external-output.ymlを作り、yqで読み戻した。
9. 観測: decisionsは空配列、q1はopen、q2はwithdrawn。外部ランタイムの入口解決・実会話・実保存を実行したという証拠にはしない。

### 負例・追加の境界例

| 入力 | 指示の適用結果 |
|---|---|
| 個別回答だけで一覧への合意なし | 内部手順3で待機。保存へ進む根拠なし |
| 「受注日」とだけ回答 | 原則38により理由の確認へ進む。出荷日の推奨理由を流用しない |
| 合意を省略して実装を要求 | この能力の成果は決定結果であると返し、未合意の結果を保存しない |
| output_toが相対パス | 公開契約の入力不備として停止。相対パスを自動補完しない |
| questionsが空 | 目的と材料から論点を探す。問いがなくても空一覧と前提を提示して合意を待つ |
| 一覧提示後に回答を修正 | 同じq1を更新し、更新一覧への合意を得直す |

## 実対話の確認状況

この改修セッションで、利用者へ「取消の締切基準を出荷日にするか」を推奨と理由付きの一問で提示した。
業務決定ではなく動作確認用の題材であると明示した。

1. 利用者の「出荷日でいい」を受け取り、理由を確認した。
2. 利用者は理由の確認へ「良い」と回答し、その後、元の質問へ「出荷日とし、その理由も採用する」と明示した。
3. 締切基準「出荷日」、理由「在庫引当の解放時点と揃えるため」、未決・取り下げなしの一覧を提示した。
4. 一覧に合意して対話テストを完了し結果を保存するかを一問で確認した。
5. 利用者の「合意して完了」を受けてから、最終YAMLを一括保存した。
6. 保存先は `/Users/naoya-nakamoriq/Documents/Github/harness-pluginsv2/grill-plugins/evals/fixtures/live-output.yml`。
7. yqで読み戻し、statusがcompleted、決定q1の回答・理由が合意一覧と一致し、open_questionsが空配列であることを確認した。

この会話での実回答から最終保存までの確認は完了した。新規インストールによる`/grill`の発見・起動や、外部ランタイムからの呼び出しは検証していない。

途中、利用者が質問UIの「Queued follow-up inputs」を指していることを取り違え、対話テストの問いを再提示した。
その後、UI表示の説明と元の質問への回答を受けた。回答・合意の代行はしていないが、UI説明の行き違いと質問の再提示があったため、円滑な操作体験まで合格とはしない。

## 制限と移行への影響

- Codex/Claudeへの新規インストールと、外部ランタイムからの実対話E2Eは未実施。AC5の全面達成は未確認。
- 旧版のスクリプト入口へ依存する呼び出し元は更新が必要。後方互換の入口は残していない。兄弟repositoryは今回変更していない。
- 対話中の状態は会話内で保持するため、会話状態そのものが失われた場合の自動復元は提供しない。
- CI定義は更新したが、GitHub上ではまだ実行していない。ここでの成功はローカル検証の結果。
- 正式仕様書はもともとdocsがignore対象だったため未追跡だった。docsを追跡対象へ追加し、仕様書の内容は変更していない。
- commit、push、リリース公開は実行していない。
